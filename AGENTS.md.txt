# Codex 작업 규칙

## 프로젝트 환경

* Unity 6000.3.23f1
* C#
* 2D
* 싱글플레이
* 네트워크 기능 사용하지 않음

Photon, Fusion, RPC, NetworkBehaviour, NetworkObject, Networked, Authority 등 멀티플레이 관련 구조를 추가하지 않는다.

---

# 역할

Codex의 역할은 사용자가 전달한 작업 지시사항을 정확하게 구현하는 것이다.

구조 설계, 기능 기획, 대안 제시를 불필요하게 하지 않는다.

사용자가 이미 정한:

* 클래스 구조
* 클래스 책임
* 데이터 흐름
* 구현 방법
* 사용 기술
* 수정 범위

을 우선하여 그대로 구현한다.

명백한 컴파일 오류, 치명적인 버그, 요구사항 충돌이 없는 한 임의로 구조를 변경하지 않는다.

---

# 작업 시작

작업 요청을 받으면 먼저 관련 파일만 확인한다.

확인 목적은 다음으로 제한한다.

* 실제 클래스 이름 확인
* 기존 API 확인
* 관련 필드와 메서드 확인
* 중복 구현 방지
* 다른 코드와 충돌 여부 확인

분석 결과를 길게 설명하지 않는다.

작업에 문제가 없다면 바로 구현한다.

---

# 수정 원칙

가능한 최소 범위만 수정한다.

하지 말아야 할 것:

* 요청하지 않은 리팩터링
* 관련 없는 코드 정리
* 임의의 아키텍처 변경
* 새로운 Manager 추가
* 새로운 Singleton 추가
* 불필요한 Interface 추가
* 불필요한 Base Class 추가
* 기존 API 이름 변경
* unrelated 파일 수정
* 요청하지 않은 기능 추가

기존 시스템을 사용할 수 있다면 재사용한다.

같은 역할의 시스템을 새로 만들지 않는다.

---

# 구현 지시 우선순위

작업 요청에 구체적인 구현 방법이 명시되어 있다면 그대로 따른다.

예:

* 특정 클래스에 기능 추가
* 특정 메서드 사용
* Stack 사용
* Event 사용
* Coroutine 사용 또는 금지
* 특정 데이터 구조 사용
* 새 클래스 생성 여부

Codex가 다른 방법을 선호하더라도 임의로 변경하지 않는다.

다만 해당 방법으로 인해 다음 문제가 발생한다면 수정 전에 간단히 알린다.

* 컴파일 불가능
* 명백한 기능 오류
* 기존 시스템과 직접 충돌
* 데이터 손실 가능성
* NullReference가 확실하게 발생
* 요구사항 자체가 서로 모순됨

---

# C# 코드 규칙

* 불필요한 public 사용 금지
* Inspector 값은 [SerializeField] 우선
* 변수와 함수 이름은 짧고 명확하게 작성
* 함수 하나는 가능한 하나의 역할만 담당
* 중복 코드 최소화
* null 가능성 확인
* 중복 실행 방지
* 이벤트 중복 구독 방지
* Coroutine 중복 실행 방지
* 불필요한 Update 사용 금지
* Update / FixedUpdate / LateUpdate 목적에 맞게 사용
* 읽기 쉬운 코드를 우선
* 기존 코드 스타일을 최대한 유지

중괄호:

public void Open()
{
isOpen = true;
}

형식을 사용한다.

---

# 주석 규칙

불필요한 주석을 추가하지 않는다.

필요한 경우에만 짧은 한국어 주석을 사용한다.

클래스 설명이 필요하면:

/// <summary>
/// 클래스 역할
/// </summary>

형식을 사용한다.

주석은:

* "~함"
* "~처리"
* "~확인"

형태로 간결하게 작성한다.

주석 끝에 마침표를 붙이지 않는다.

---

# Unity 규칙

2D 프로젝트이므로 기본적으로:

* Collider2D
* Rigidbody2D
* Physics2D
* RaycastHit2D

를 사용한다.

요청하지 않는 한 3D Physics를 사용하지 않는다.

Scene, Prefab, ProjectSettings, Packages는 작업에 반드시 필요한 경우가 아니면 수정하지 않는다.

---

# 작업 검증

* 사용자 지침: 앞으로 `Verification` 스크립트는 생성하지 않는다

구현 후 수정한 코드만 중심으로 확인한다.

반드시 확인:

* 컴파일 오류 가능성
* NullReference 가능성
* 잘못된 메서드/필드 이름
* 기존 API와의 충돌
* 이벤트 중복 구독
* Coroutine 중복 실행
* 잘못된 Unity 참조
* 요구사항 누락

실제로 실행하거나 컴파일하지 않았다면 실행했다고 말하지 않는다.

---

# 코드 가독성 및 줄 수 규칙

가독성을 최우선으로 하되, 단순히 보기 좋게 만들기 위해 불필요하게 코드 줄 수를 늘리지 않는다.

* 의미 없는 줄바꿈을 하지 않는다
* 간단한 표현을 여러 줄로 분리하지 않는다
* 한 줄로 읽기 쉬운 코드는 한 줄로 유지한다
* 변수 선언과 단순 대입 사이에 불필요한 빈 줄을 넣지 않는다
* 관련된 코드는 가능한 가까이 배치한다
* 코드 블록 사이에 과도한 빈 줄을 만들지 않는다
* 단순한 조건이나 메서드 호출을 가독성이라는 이유만으로 여러 줄로 분리하지 않는다
* 지나치게 압축하여 읽기 어렵게 만드는 것도 피한다

## 함수 선언 규칙

함수 선언부는 반드시 한 줄로 작성한다.

매개변수가 여러 개 있더라도 함수 선언을 여러 줄로 분리하지 않는다.

사용하지 말 것:

```csharp
private void MoveItem(
    int index,
    float duration,
    bool immediate)
{
    // ...
}
```

사용할 것:

```csharp
private void MoveItem(int index, float duration, bool immediate)
{
    // ...
}
```

함수 본문은 필요한 로직에 따라 일반적인 C# 형식으로 작성한다.

함수 본문 전체를 억지로 한 줄로 압축하지 않는다.

사용하지 말 것:

```csharp
private void Open() { isOpen = true; UpdateUI(); PlaySound(); }
```

사용할 것:

```csharp
private void Open()
{
    isOpen = true;
    UpdateUI();
    PlaySound();
}
```

## 핵심 기준

코드를 짧게 만드는 것이 목적이 아니다.

다음 두 가지를 동시에 만족시킨다.

* 읽기 쉬움
* 불필요하게 세로로 길지 않음

가독성을 이유로 의미 없이 줄 수를 늘리지 않고, 줄 수를 줄이기 위해 복잡한 로직을 한 줄에 몰아넣지도 않는다.

# 응답 규칙

설명을 최소화한다.

작업 완료 후 다음 형식으로만 간단히 보고한다.

## 완료

* 수정한 파일
* 생성한 파일
* 구현한 핵심 내용

## 확인 필요

Unity Inspector에서 사용자가 직접 설정해야 하는 항목이 있을 때만 작성한다.

## 주의

실제로 발견한 문제나 사용자가 알아야 하는 사항이 있을 때만 작성한다.

문제가 없다면 생략한다.

장문의 구조 설명, 데이터 흐름 설명, 설계 해설은 하지 않는다.

---

# 최우선 규칙

사용자의 작업 지시사항을 정확히 구현한다.

더 좋은 구조를 새로 설계하는 것이 목적이 아니다.

요청된 기능을 기존 프로젝트에 최소한의 변경으로 정확하게 적용하는 것이 목적이다.
